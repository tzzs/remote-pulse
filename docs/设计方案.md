# Remote Pulse — 产品与技术方案

## 0. 插件命名

**名称:Remote Pulse(中文:远程脉搏)**

- **package name / 唯一标识:** `remote-pulse`
- **VSCode 命令前缀 / 配置命名空间:** `remotePulse.*`
- **命名理由:**
  - "Pulse"(脉搏/心跳)直接呼应设计中采用的 `$(pulse)` codicon 和"呼吸感"的监控隐喻——安静存在、有异常才跳动提醒你,这正是要复刻的原生延迟指示器式体验
  - 不含 "SSH"/"Monitor" 这类被市面同类插件(SSH Remote Monitor、Remote Server Status、Monitor Pro)高度复用的词,便于在 Marketplace 搜索结果中形成品牌辨识度
  - 简短(2 个单词),状态栏和命令面板中出现时不显冗长

## 1. 产品概述

### 1.1 背景与问题
使用 Remote-SSH 开发时,远程服务器的负载状态是黑盒——用户需要额外开一个终端跑 `top`/`htop` 才能知道当前是否在跑重任务(编译、训练、构建)、机器是否过载。这打断了编码心流,也容易忽略资源异常(比如后台进程 OOM 前的内存暴涨)。

### 1.2 目标用户
- 通过 Remote-SSH 连接云主机/工作站/GPU 服务器开发的个人开发者
- 常见场景:本地 Windows/Mac 通过 SSH 连高算力 Linux 服务器(编译、AI 训练、数据处理)

### 1.3 核心价值主张
在不打断编码流程的前提下,以 VSCode 原生延迟指示器般"安静但随时可查"的方式,持续感知远程机器的健康状态。

### 1.4 与现有插件的差异化定位
市面上的方案(SSH Remote Monitor、Remote Server Status、Monitor Pro 等)多是"仪表盘搬进状态栏",信息密度偏高、常驻显示较重。本方案的差异化:

| 维度 | 现有插件普遍做法 | 本方案 |
|---|---|---|
| 常驻信息量 | CPU\|MEM\|DISK 全部平铺 | 默认只有 1 个 icon + 1 个核心数字,其余进 tooltip |
| 视觉基调 | 数值常态化配色 | 默认中性色,仅越阈值才变色告警 |
| 交互 | 部分需开侧边栏 | 点击弹出轻量 QuickPick/Webview,不占用常驻空间 |
| 资源开销 | 部分用 spawn 子进程 | 直读 `/proc`,零子进程常态开销 |
| 场景感知 | 前后台一致轮询 | 窗口失焦自动降频 |

### 1.5 完整功能范围

Remote Pulse 的完整功能集如下,状态栏始终只暴露 1 个核心数字(理念不变),但 tooltip / 趋势面板承载全部指标:

| 模块 | 内容 | 数据来源 |
|---|---|---|
| CPU | 总体使用率、每核使用率、核心数 | `/proc/stat` 增量计算 |
| 内存 | 使用率、已用/总量、buffer/cache 占比 | `/proc/meminfo` |
| 磁盘 | 各挂载点使用率与容量(支持指定挂载点或自动选 Top N) | `statvfs`(`fs.statfs`)遍历 `/proc/mounts` |
| 网络 | 上行/下行速率 | `/proc/net/dev` 增量计算 |
| GPU | 显存占用、利用率、温度(如有 NVIDIA 卡) | 解析 `nvidia-smi --query-gpu=... --format=csv` 输出 |
| Docker | 运行中容器数、各容器 CPU/内存占用 | Docker Engine API(`/var/run/docker.sock`),无 socket 权限时优雅降级为不显示该模块 |
| 多主机会话 | 每个 Remote-SSH 窗口独立追踪对应主机,互不干扰 | 天然继承自 workspace extension host 的隔离机制 |
| 阈值告警 | CPU/内存/磁盘任一超阈值时状态栏变色 + 可选系统通知 | 基于配置的 warning/critical 阈值判断 |
| 历史趋势 | tooltip 内 sparkline + 点击弹出的 Webview 折线图 | RingBuffer 环形缓冲区 |

设计原则不因功能变多而妥协:**状态栏常驻展示始终克制**(默认仍只显示 1 个核心指标),GPU/Docker 等重量级采集(需要 spawn 子进程或走 socket)统一走**独立的低频轮询通道**,不与 CPU/内存的高频 `/proc` 轮询混在一起,避免拖累核心体验的实时性。

## 2. 用户体验设计

### 2.1 状态栏展示 —— 对齐原生延迟指示器的视觉语言

VSCode 原生的 Remote-SSH 延迟指示器长这样:一个 icon + 一个短数字,平时几乎不引人注意,只有异常(高延迟)时才变红。这是本插件要复刻的核心体验。

**默认态(正常负载):**
```
$(pulse) 23%
```
只显示 CPU 使用率一个数字,用 codicon `pulse`(呼吸感强,呼应"心跳"式监控)。宽度用 `padStart(2, ' ')` 固定为两位数,避免刷新时数字从 `9%` 跳到 `23%` 造成状态栏图标横向抖动。

**告警态(超阈值):**
```
$(warning) 92%   ← 背景变 statusBarItem.warningBackground / errorBackground
```
颜色语义严格遵守"只在异常时着色"原则,平时不用任何背景色,避免"狼来了"效应削弱告警的注意力权重。

**多远程会话:** 如果本地同时开多个 Remote-SSH 窗口,每个窗口的状态栏只显示当前连接的那台机器,不做跨窗口聚合(保持简单)。

### 2.2 悬浮 Tooltip —— 详情的容器

鼠标悬停展开 `MarkdownString`,详情包括:

```
远程主机: dev-gpu-01 (192.168.x.x)
─────────────────────
CPU   ▁▃▅▇▆▄▂  23%  (8 核)
内存  ▂▂▃▄▄▃▂  61%  (9.8G / 16G)
Uptime  12d 4h
─────────────────────
点击查看趋势图
```

用 unicode 块字符(▁▂▃▅▇)画迷你 sparkline,不需要额外起 Webview 就能表达趋势,这是保持"轻"的关键技巧。

### 2.3 点击交互
点击状态栏项 → 弹出一个小型 Webview 面板(而非常驻侧边栏),展示:
- 过去 30 分钟 CPU/内存曲线(Canvas 2D 折线图,参考 Monitor Pro 的做法但只做单机、不做多指标堆叠)
- 关闭后不留痕迹,避免占用编辑区

### 2.4 配置项设计(体现"可裁剪"理念)

```jsonc
{
  "remotePulse.refreshInterval": 2000,        // 前台高频指标刷新间隔(ms): CPU/内存
  "remotePulse.backgroundInterval": 15000,     // 失焦后降频间隔
  "remotePulse.heavyMetricInterval": 10000,    // GPU/Docker 等低频指标独立轮询间隔
  "remotePulse.statusBarMetric": "cpu",        // 状态栏主指标: cpu | memory
  "remotePulse.warningThreshold": 80,          // 告警阈值 %
  "remotePulse.criticalThreshold": 95,         // 严重阈值 %
  "remotePulse.template": "$(pulse) ${value}%",// 自定义显示模板
  "remotePulse.enableGpu": true,               // 是否探测并展示 GPU 信息
  "remotePulse.enableDocker": true,            // 是否探测并展示 Docker 容器信息
  "remotePulse.enableNetwork": false,          // 是否展示网络速率(默认关,减少 tooltip 噪音)
  "remotePulse.diskMountPoints": []            // 指定要监控的挂载点,留空则自动选 Top N
}
```

### 2.5 边界情况的体验处理
- **非 Linux 远程主机:** 检测平台后自动隐藏指标,tooltip 提示"当前系统暂不支持资源监控",不报错、不崩溃
- **首次连接采集延迟:** 状态栏先显示 `$(sync~spin)` 加载态,而不是空白或 `--`
- **采集失败(权限/网络抖动):** 显示 `$(circle-slash)`,tooltip 说明原因,不弹烦人的错误通知

## 3. 技术架构

### 3.1 整体架构

```
┌─────────────────────────────────────────────┐
│  本地 VSCode UI (Local Extension Host)        │
│  — 无需任何逻辑,纯粹渲染由远端 host 推来的状态 —  │
└─────────────────────────────────────────────┘
                    ▲ IPC (VSCode 内部机制,自动处理)
┌─────────────────────────────────────────────┐
│  远程 Workspace Extension Host (跑在远程机器上) │
│                                               │
│  ┌────────────────┐  ┌────────────┐  ┌─────────┐ │
│  │ Collector (轻量) │→│ StatsStore  │→│StatusBar│ │
│  │ CPU/内存/磁盘/网络 │  │ 环形缓冲区   │  │ 渲染器   │ │
│  │ 直读 /proc        │  └────────────┘  └─────────┘ │
│  └────────────────┘         ↑              ↓        │
│  ┌────────────────┐  ┌───────────┐   ┌─────────┐  │
│  │ Collector (重量) │→│ Scheduler  │   │ Webview │  │
│  │ GPU/Docker       │  │ 双通道轮询  │   │ 趋势面板 │  │
│  │ spawn / socket    │  └───────────┘   └─────────┘  │
│  └────────────────┘                                  │
└─────────────────────────────────────────────┘
```

关键点:插件声明为 `"extensionKind": ["workspace"]`,VSCode 会自动把它调度到远程 extension host 运行,采集到的 `os`/`fs` 数据天然就是远程机器的——**不需要自己维护 SSH 连接或额外协议**,这是复用平台机制而非重新发明轮子。

Collector 分成"轻量"与"重量"两类,分别接入独立的轮询通道(见 3.4),这样 GPU/Docker 的采集开销不会拖慢 CPU/内存这类核心高频指标的响应速度。

### 3.2 数据采集层(Collector)

**CPU 使用率算法(增量法,而非 loadavg):**
```typescript
// 读取 /proc/stat 第一行: cpu  user nice system idle iowait irq softirq
function readCpuTimes(): CpuTimes {
  const line = fs.readFileSync('/proc/stat', 'utf8').split('\n')[0];
  const [, user, nice, system, idle, iowait, irq, softirq] = line.trim().split(/\s+/).map(Number);
  const idleTime = idle + iowait;
  const totalTime = user + nice + system + idle + iowait + irq + softirq;
  return { idleTime, totalTime };
}

function calcCpuUsage(prev: CpuTimes, curr: CpuTimes): number {
  const idleDelta = curr.idleTime - prev.idleTime;
  const totalDelta = curr.totalTime - prev.totalTime;
  return totalDelta === 0 ? 0 : (1 - idleDelta / totalDelta) * 100;
}
```
两次采样做差值,比读 `loadavg` 更贴近"此刻"的真实占用,且不受历史 1/5/15 分钟平滑的滞后影响。

**内存使用率:**
```typescript
// 解析 /proc/meminfo 的 MemTotal / MemAvailable(比 MemFree 更准确,
// 因为 Linux 会把可回收的 buffer/cache 算作"可用")
function readMemUsage(): MemStats {
  const content = fs.readFileSync('/proc/meminfo', 'utf8');
  const total = parseMemLine(content, 'MemTotal');
  const available = parseMemLine(content, 'MemAvailable');
  const used = total - available;
  return { total, used, percent: (used / total) * 100 };
}
```

**为什么不用 spawn 子进程(`top -bn1` / `ps`):**
- 子进程创建有 fork/exec 开销,1~2 秒轮询一次会持续消耗远程机器资源,与"监控工具本身不该成为负载来源"的原则冲突
- `/proc` 是内核维护的只读文件,`fs.readFile` 开销接近于零
- 唯一例外:如果要支持非 Linux(如 SSH 到 macOS 主机),`/proc` 不存在,需要 fallback 到 `os.cpus()` 轮询(Node 内置,跨平台但精度略低)

**磁盘:**
```typescript
// 解析 /proc/mounts 拿到挂载点列表,再用 fs.statfs 逐个查容量
async function readDiskUsage(mountPoint: string): Promise<DiskStats> {
  const stats = await fs.promises.statfs(mountPoint);
  const total = stats.blocks * stats.bsize;
  const free = stats.bavail * stats.bsize;
  return { mountPoint, total, used: total - free, percent: ((total - free) / total) * 100 };
}
```
默认只展示根分区 + 使用率 Top N 的挂载点,避免 tooltip 被十几个挂载点淹没。

**网络:**
```typescript
// /proc/net/dev 累计字节数做增量,除以采样间隔得到速率
function readNetworkDelta(prev: NetSample, curr: NetSample, intervalSec: number) {
  return {
    rxRate: (curr.rxBytes - prev.rxBytes) / intervalSec,
    txRate: (curr.txBytes - prev.txBytes) / intervalSec,
  };
}
```

**GPU(需要 spawn 子进程,是"重量级 Collector"的代表):**
```typescript
// nvidia-smi --query-gpu=utilization.gpu,memory.used,memory.total,temperature.gpu --format=csv,noheader,nounits
async function readGpuStats(): Promise<GpuStats[]> {
  const { stdout } = await execFileAsync('nvidia-smi', [
    '--query-gpu=utilization.gpu,memory.used,memory.total,temperature.gpu',
    '--format=csv,noheader,nounits',
  ]);
  return stdout.trim().split('\n').map(parseGpuLine);
}
```
启动时先探测 `nvidia-smi` 是否存在(`which nvidia-smi` 或直接 try/catch 执行一次),不存在则该模块整体不激活,不反复重试浪费资源。

**Docker:**
通过 Docker Engine 的 Unix Socket(`/var/run/docker.sock`)调用 `GET /containers/json` 和 `GET /containers/{id}/stats?stream=false`,用 Node 原生 `http.request` 配 `socketPath` 参数即可,不依赖 Docker CLI 或额外 SDK。若 socket 不存在或无权限访问,直接跳过该模块并在 tooltip 里静默隐藏,不报错。

### 3.3 状态管理层(StatsStore)
用固定长度的环形缓冲区(如保存最近 900 个采样点,对应 30 分钟 @ 2秒/次)存储历史数据,供 Webview 趋势图和 tooltip sparkline 使用,避免无限增长导致内存泄漏——具有讽刺意味的是,监控内存的插件不该自己造成内存问题。

```typescript
class RingBuffer<T> {
  private buf: T[] = [];
  constructor(private capacity: number) {}
  push(item: T) {
    this.buf.push(item);
    if (this.buf.length > this.capacity) this.buf.shift();
  }
  toArray(): T[] { return [...this.buf]; }
}
```

### 3.4 调度层(Scheduler)—— 双通道自适应轮询

轻量指标(CPU/内存/磁盘/网络)和重量指标(GPU/Docker)使用两条独立的定时器通道,互不阻塞:

```typescript
vscode.window.onDidChangeWindowState((state) => {
  const lightInterval = state.focused
    ? config.get('refreshInterval')       // 前台 2s
    : config.get('backgroundInterval');   // 失焦 15s(甚至可暂停)
  const heavyInterval = state.focused
    ? config.get('heavyMetricInterval')   // 前台 10s(GPU/Docker 天然变化慢,不需要秒级)
    : config.get('backgroundInterval') * 2;

  lightScheduler.reschedule(lightInterval);
  heavyScheduler.reschedule(heavyInterval);
});
```
窗口失焦时降频甚至暂停,原因:
1. 用户看不到状态栏时,高频采集没有意义
2. 减少对远程机器本身的干扰(尤其是本身就在做重计算的机器)
3. 重量指标(spawn 子进程 / socket 调用)本身开销更大,轮询间隔天然应比轻量指标更长,双通道设计让两者可以独立调优,不互相拖累

### 3.5 渲染层
- `StatusBarItem` 用 `vscode.window.createStatusBarItem`,`text`/`color`/`backgroundColor` 按阈值动态更新
- Tooltip 用 `MarkdownString`(`isTrusted: false`,避免不必要的安全面)
- Webview 趋势面板按需创建、按需销毁(`retainContextWhenHidden: false`),不常驻内存

### 3.6 打包与发布
- 用 `vsce package` 打包为 `.vsix`
- `package.json` 关键字段:
```jsonc
{
  "extensionKind": ["workspace"],
  "activationEvents": ["onStartupFinished"],
  "capabilities": { "virtualWorkspaces": false }
}
```
- 发布到 VS Code Marketplace(需 Azure DevOps PAT)或先以 `.vsix` 私分发验证需求

## 4. 性能与稳定性保障

| 风险点 | 应对策略 |
|---|---|
| 高频轮询拖累远程机器 | 自适应间隔 + 默认 2s 不做到 1s |
| 采集异常导致插件崩溃 | Collector 层全量 try/catch,失败降级为"不可用"态而非抛异常 |
| 环形缓冲区内存增长 | 固定容量,超出自动丢弃最旧数据 |
| 多窗口重复采集 | 每个 workspace extension host 独立生命周期,天然隔离,无需额外去重逻辑 |
| 非 Linux 远程主机崩溃 | 启动时探测 `/proc` 是否存在,不存在则走精简 fallback 或提示不支持 |

## 5. 建议开发顺序

不按"版本"划分,而是按依赖关系和验证价值排列实现顺序,全部完成后即为完整产品:

1. **核心骨架**:extension 激活、`extensionKind: workspace` 配置、StatusBarItem 占位显示
2. **CPU 采集与展示**:`/proc/stat` 增量算法 + 状态栏渲染 + 阈值变色 —— 这一步就能验证核心交互体验是否符合"原生延迟指示器"的手感,是后续一切的地基
3. **内存采集**:`/proc/meminfo` 解析,复用同一套 Collector/StatsStore 抽象
4. **自适应调度**:窗口焦点监听 + 双通道轮询,补齐性能保障
5. **Tooltip 详情 + sparkline**:验证 RingBuffer 存取与 Markdown 渲染
6. **Webview 趋势面板**:点击交互 + Canvas 折线图
7. **磁盘 + 网络采集**:复用轻量 Collector 模式,风险最低,可并行推进
8. **GPU 采集**:引入"重量 Collector"通道和子进程调用,验证降级逻辑(无 GPU 时优雅隐藏)
9. **Docker 采集**:引入 socket 调用,验证权限缺失时的静默降级
10. **配置项收口 + 边界情况打磨**:非 Linux 远程、采集失败态、多窗口隔离逐一测试
11. **打包发布**:`vsce package` → Marketplace 上架或 `.vsix` 分发

第 2~4 步验证的是产品最核心的体验假设,建议优先跑通并自用一段时间再继续往后扩展模块,避免在核心手感未验证前就铺开全部指标。

## 6. 风险与限制
- 仅支持 Linux 远程主机是明确边界,BSD/macOS 远程需要 fallback 到 `os.cpus()` 等跨平台 API,精度会打折扣
- 高权限受限的容器环境(部分 `/proc` 字段被 cgroup 限制/隐藏)需要额外兼容测试
- GPU 监控依赖 `nvidia-smi` 存在,AMD/Intel 显卡需要额外适配(`rocm-smi`/`intel_gpu_top`),现阶段不在设计范围内
- Docker 监控依赖当前用户对 `/var/run/docker.sock` 有读权限,很多生产环境会限制此权限,需在文档中明确说明这是可选降级项
- Marketplace 上已有多个同类插件,如果目标是发布而非自用,需要在描述/图标/极简体验上做出可感知的差异化,才能在搜索结果里被看到
